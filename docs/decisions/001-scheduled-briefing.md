# ADR-001: 예약 작업으로 보안 사건 요약 발송

## 상태

승인됨 — 2026-10-25 사용자와 합의 후 구현.

## 배경

개인용 서비스로 하루 한 분야의 보안 동향을 디스코드에서 읽는다. 모든 분야를 매시간 수집하며, 발송 단위는 기사 한 건에서 여러 사건을 묶은 요약으로 변경됐다. 정확성, 이미 보낸 사실의 중복 방지, 원문 접근성과 비용 가시성이 우선이다.

## 결정

AWS Scheduler/Lambda/SQS/DynamoDB/S3로 구성한다. Spring Boot를 사용하는 EC2 두 대(Bastion/NAT와 프라이빗 앱)보다 상시 비용과 OS 운영 부담이 작은 예약 작업을 선택했다. VPC 연결이나 NAT Gateway는 필요하지 않다. Python은 원문 추출 도구를 활용하기 위해 선택했다.

수집과 분석은 FIFO 큐로 분리한다. 한 메시지 그룹과 Processor 동시 실행 1개로 사건 통합 경쟁을 줄인다. 한 원문이 긴 실행을 차지해도 다른 수집 작업을 막지 않는다. 실패는 최대 세 번 수신 후 DLQ로 이동한다.

### 선정 규칙

다섯 분야를 순환한다. 새 사건은 영향력 40, 구체적 위협 30, 새로운 사실 20, 최신성 10점으로 평가한다. 미발송 사건은 발표일로부터 14일간 유지한다. 최신 소식이 있으면 오래된 미발송 사건은 최대 1건 보충한다. 없으면 미발송 사건만으로 구성한다. 해당 분야에서 검증을 통과한 사건이 하나도 없으면 다음 분야로 진행한다. 순환 포인터는 실제 선택한 분야 다음으로 이동한다.

긴급 사건 최대 1건을 맨 앞에 포함하고, 일반 사건을 최대 4건으로 제한한다. 이미 발송한 사건의 단순 재보도는 제외한다. 패치·실제 악용·피해 범위 변경·정정 등 중요한 변화만 후속으로 허용한다. 보충 기사의 발표일을 표시한다.

### 근거와 이력

제목이나 검색 스니펫은 요약 입력으로 쓰지 않는다. 원문을 확보하고 정확한 인용 구절이 본문에 있는지 검사한다. 검증 대상 요약은 문장마다 사실 ID를 갖고, 발송 시 원문 번호와 URL로 표시한다. 발송 직전 준비 단계에서 원문을 다시 가져와 정정·삭제 여부를 검토한다. AI가 생성한 미검증 제목은 최종 메시지에 사용하지 않는다.

`ARTICLE#urlhash`는 URL의 최근 본문 해시, `CONTENT#hash`는 동일 본문 중복을 기록한다. `EVENT`와 `FACT#event`는 사건·근거를, `INDEX#identifier`는 과거 사건 검색을, `SENT#fact`와 `SENT_EVENT#event`는 전달한 사실을 기록한다. 본문 전체는 S3 수명 주기로 30일 후 만료되며, 짧은 근거 인용과 사실 기록은 유지한다.

일일 준비는 영구 보관되는 `EVENT` 전체를 조회하지 않는다. 발행일 UTC 기준 `CANDIDATES#YYYY-MM-DD` 파티션에 사건 ID를 기록하고, 16일 TTL로 정리한다. 준비 작업은 최근 14일과 하루 이내 미래 날짜의 파티션만 읽은 뒤 해당 사건과 근거를 가져온다. 사건 중복 비교에는 `RECENT_EVENTS#YYYY-Www` 주간 파티션을 사용하며, 한 사건은 주간 파티션마다 한 행만 저장한다. 최대 5개 주간 파티션에서 사건 ID별 최신 시각으로 중복 제거한 뒤 40개로 제한한다. 이 인덱스는 35일 TTL로 정리한다.

리뷰 후 보완: 기사 처리 완료·사실·사건·검색 인덱스를 DynamoDB 트랜잭션으로 함께 저장한다. 재실행 시 동일 본문 처리 완료 레코드를 조건으로 사용해 중간 저장 실패나 응답 유실에도 일관성을 유지한다.

사건에는 `revision`을 부여한다. 중요한 변화가 있어야 버전을 증가시키고, 중요하지 않은 보충 설명은 미발송 중인 동일 버전에 추가한다. 사건의 마지막 메시지를 확인한 뒤 `HANDLED#event`에 처리한 버전을 기록한다. 이는 `SENT#fact`와 별개다. 실제 보낸 사실만 SENT에 기록하고, 요약에서 생략한 해당 버전의 사실은 다시 선정하지 않는다. 준비 이후에 수집한 더 높은 버전은 처리 완료로 덮어쓰지 않는다.

중복 비교는 모든 과거 사건을 매번 읽지 않고 정확한 사건 키, 식별자 인덱스, 최근 사건 목록을 사용한다. 상위 24개 후보의 전체 사실을 요청당 약 24,000자 이력으로 분할해 비교한다. 후보 선택은 제한되지만 선택된 사건의 오래된 사실은 자르지 않는다. 여러 요청이 서로 다른 사건을 동일 사건이라고 판단하면 안전하게 실패시킨다.

### 발송과 실패

초안을 먼저 저장하고 09시부터 발송한다. 각 메시지에 대해 DynamoDB 조건부 갱신으로 `sending` 상태를 선점한 뒤 웹훅 `wait=true` 응답의 메시지 ID를 저장한다. 성공한 메시지는 다시 보내지 않는다. 429는 서버의 재시도 시간을 따른다. 연결 전 실패는 재시도한다. 전송 도중 시간 초과·응답 유실·서버 오류는 `unknown`으로 보류한다. `sending` 상태에서 실행이 종료돼도 자동 재전송하지 않는다.

이는 정확히 한 번 전달 보장이 아니다. 중복을 피하기 위해 드문 누락을 허용한다는 사용자의 선택이다. 미해결 일일 초안에 포함된 사건은 다음 초안에서도 보류하여 결과 불명 사건이 새 요약으로 다시 나가지 않게 한다.

리뷰 후 보완: 일시적인 본문·AI 오류는 오전 9시 전에 재시도하며, 근거가 부족한 사건과 구분한다. 9시 이후 최종 준비에서도 실패하면 다른 분야를 검토하고 검증된 후보가 없으면 상태 안내를 만든다. 메시지 분할 시 원문 URL은 절대 자르지 않는다. 메시지 한도보다 긴 URL은 오류로 처리한다.

지난 초안은 관리자가 채널을 확인한 뒤 `complete` 또는 `cancel`로 닫을 수 있다. 결과 불명 메시지가 남아 있으면 취소하지 못한다. 완료는 모든 메시지의 도착 확인을 요구하며 실제 보낸 사실·처리 버전을 복구한다. 취소 시 전혀 노출되지 않은 사건은 다시 후보가 된다. 개요나 본문 일부라도 노출된 사건은 같은 내용을 다시 보내지 않도록 해당 버전을 처리 완료로 닫는다. 더 새로운 버전은 영향을 받지 않는다. 과거 초안 복구가 최신 분야 순서나 비용 보고 기준을 되돌리지는 않는다.

### 비용

Haiku 호출마다 토큰·모델·단가·작업 종류를 기록한다. 일일 보고는 직전 비용 보고 이후와 한국 시간 기준 월 누계를 포함한다. 예산 80%/100%에서 경고하지만 AI 호출이나 발송을 중단하지 않는다. 실제 AWS 비용은 AI footer에 포함하지 않는다.

## 대안과 영향

- EC2 두 대: Spring Boot 운영과 네트워크 학습에 유용하지만 현재 작업에 상시 서버가 필요하지 않고 고정 비용이 커 제외했다.
- 단순 기사 우선순위 큐: 오래된 기사가 최신 기사를 밀고 분야가 편중돼 제외했다.
- 미발송 사건 즉시 폐기: 중요한 뉴스를 영영 놓칠 수 있어 14일 보충 후보로 변경했다.
- 실패 시 무조건 재전송: 응답 유실 때 중복이 발생하므로 결과 불명 상태를 분리했다.
- 조회 화면·사용자 읽음 추적: 첫 버전 범위 밖이다. 놓침은 읽지 않음이 아니라 미발송을 뜻한다.
